Engineering decision record · NEONOVA-1264

LiteLLM vs Bifrost
Internal AI Gateway Evaluation

Researched 2026-10-23 Scope internal gateway · ~100 users · 1 WhatsApp chatbot team Status LiteLLM OSS v1.106.2 POC in production-candidate trial Alternative maximhq/bifrost (Go)
Decision baseline (our hard requirements): virtual keys + per-key/per-team max_budget with soft_budget; SQL-queryable spend logs with per-token pricing declared per model alias; admin UI with local accounts (email+password, no SSO); Postgres; team-level key issuance + per-key model allowlist; OpenAI-compatible API; DashScope/Qwen provider. Every claim links a primary source; anything that could not be confirmed from primary sources is flagged in section 9.
Keep LiteLLM. Do not switch to Bifrost.
  • Multi-user local-account admin UI — Bifrost OSS ships a single admin account only; multiple users require Enterprise and force an IdP (OIDC/SCIM)
  • Native DashScope/Qwen — Bifrost has no dashscope provider (only 172 qwen pricing entries in its datasheet); the only path is a custom provider on the openai base
  • Declarative per-alias pricing — our model_list[].model_info pattern is native LiteLLM; Bifrost requires maintaining separate pricing_overrides objects
Bifrost's real gain is operational weight (single binary / SQLite, no external DB / 85MB image / 6s cold start), not performance — for a ~100-user internal gateway both are far beyond need. If migration is ever triggered, an official LiteLLM migration CLI brings switching cost down to days, not months.

02Architecture & runtime

LITELLM — Python

  • proxy + SDK in one repo, plus a Rust core (officially beta)
  • Hard Postgres dependency: keys/budgets/spend all live in the DB; without one, budgets fail open
  • Config: config.yaml + Postgres; admin UI at /ui
  • Deployment: Docker / Helm / cloud templates

BIFROST — Go

  • Single static binary with embedded React UI
  • Three independent stores: config_store (SQLite default) / logs_store (+PG/ClickHouse) / vector_store (semantic cache only)
  • Dual config mode: UI/DB mode, or file-only config.json (declarative bootstrap, hash-reconciled with the DB)
  • Governance/logging are built-in plugins; semantic cache / otel etc. are opt-in
Documentation contradiction (needs live testing)
Bifrost's OSS config.json governance page says "Governance enforcement is always active in OSS", while the Helm page says the governance plugin "must be enabled". Actual behavior wins.

03Governance, requirement by requirement deep dive

Budgets / soft budgets

LiteLLM: key-level max_budget + budget_duration + soft_budget (fires a Slack alert); team overage returns 422 budget_exceeded. Key detail: when a key belongs to a team, only team budgets are enforced — the owner's personal budget is not (since v1.95.0). Bifrost: four budget layers validated additively; any insufficient layer rejects. VKs can stack per-model limits. No soft_budget, and no OSS alerting channel.

Spend logs & pricing

LiteLLM's LiteLLM_SpendLogs is directly SQL-queryable; per-alias per-token prices live in model_list[].model_info (including cache/image/audio/reasoning-token splits). Bifrost logs are SQL-queryable and filterable via /api/logs (including content_search); pricing goes through pricing_overrides with ten scopes, most-specific wins.

Admin UI & auth the decisive gap

Bifrost's OSS UI is feature-complete (provider config, live logs, VK/budget pages), but the auth model differs: a single admin username/password plus a setup_token needed to create the first admin; by default, an instance without a password opens the dashboard directly. Multi-user, local user directories, RBAC, audit logs, SSO/SCIM are all Enterprise — the OSS Users page is literally an "Unlock users & user governance — enterprise license" placeholder. The "local user directory without SSO" we need is only offered by LiteLLM OSS.

Migration path (if we ever switch)

Official CLI: npx @maximhq/bifrost-migration-cli reads the LiteLLM management API + config.yaml (optional Postgres), migrating models / orgs→customers / teams / internal users / virtual keys (model allowlists fold onto VKs), with DRY_RUN=1 and idempotent re-runs. Known limits: no org-level model gate, partial-wildcard models skipped, custom api_bases on non-openai/anthropic/gemini/bedrock bases skipped. Switching cost drops from months to days — but it does not close a capability gap.

04Provider support DashScope / Qwen

LiteLLM natively covers all Qwen models via dashscope/, plus qwencloud/ and qwen_ai_platform/ prefixes; both the China and international compatible-mode base URLs are supported. Our POC runs on dashscope/ compatible-mode today.

Bifrost's core/providers/ holds 34 providers, none of them dashscope / qwen / aliyun; yet its pricing catalog already carries dashscope/* (58), qwencloud/* (56), and qwen_ai_platform/* (58) entries — pricing is ready, the provider implementation is missing. Viable approaches:

  • Custom provider: base_provider_type="openai" + compatible-mode base_url (roughly an hour to a working setup)
  • OpenRouter relay (the catalog carries many qwen entries)
  • Contribute a native provider upstream (model on cerebras/ or groq/; moderate effort)

Verdict: not out-of-the-box, not impossible — the cost is losing officially maintained parameter compatibility.

06Security & supply-chain record

Both are tainted, but in different ways: LiteLLM suffered a compromised release pipeline; Bifrost shipped unsafe defaults.

  • 2026-03 · LiteLLM
    1.82.7 / 1.82.8 poisoned builds
    Introduced via a trivy scanning step, same GHSA — not an isolated incident
  • 2026-10-21 · LiteLLM
    v1.107.0 release-pipeline poisoning (GHSA-92x9-889m-jgmw)
    The attacker obtained 3 developers' GitHub OAuth tokens (one an org owner), disabled branch protection, and pointed the release source at a lookalike repo Berri-AI/litellm (extra hyphen). All 7 PyPI wheels were exposed for 1h44m; Docker Hub/GHCR tags v1.107.0/latest/main-latest/main-stable were poisoned in the same window. The cook.pth payload was a credential stealer (16 modules, directly querying LiteLLM_CredentialsTable) plus a second-stage RCE. Official remediation: reinstall and pin 1.106.2, rotate all credentials. Self-admitted process flaws: temporarily relaxed release permissions and an internal proxy exposed to the public internet
  • Patched · Bifrost
    CVE-2026-90898 (CVSS 9.8) + CVE-2026-86242
    Unauthenticated MCP stdio client / custom plugin registration → RCE inside the container. Root cause: auth_config.is_enabled=false by default (no password). Fixed in v2.1.0: unauthenticated registrations return 403, setup_token introduced
  • Ongoing · Bifrost
    Supply-chain practices
    Actions SHA pinning + npm provenance, Snyk/CodeQL/Docker Scout, FIPS base image, non-root. No known poisoning incident of its own ("not found" ≠ "proven absent")
What this means for us
Our POC runs 1.106.2 — exactly the officially designated safe version, pulled on 10-23 with no exposure to 1.107.x, so no cook.pth window and key rotation is not required. But we must pin the version + verify the image digest and forbid floating tags like latest / main-stable (latest was poisoned too).

08Trade-offs for our scenario

The cost of keeping LiteLLM (quantified)
Hard Postgres dependency (we already run PG, so ≈ 0); Python runtime: ~25s cold start / ~1.5GB RAM / 365MB image (third-party measurements — perfectly acceptable for a ~100-user internal gateway); version chaos → pin version + digest + staged upgrades; enterprise gaps (SSO>5 users, audit logs, enforced_params, key tags) — not on our critical path today, but a future SSO/compliance push hits that wall and triggers re-evaluation.

What switching to Bifrost would buy

  • Zero external DB to start (SQLite) + single binary + 85MB image + 6s cold start → lower ops and DR cost
  • 4–10x RPS/overhead ("nicer than needed" at our scale)
  • Finer budget hierarchy, deny-by-default + regex: allowlists, budget overrides
  • Native semantic caching (needs a vector store) and async inference
  • The official migration CLI brings switching cost down to engineering-days

Near-term actions (without switching)

  1. Lock the POC down: litellm==1.106.2 + image digest pinning; forbid floating tags (we currently pin the tag, which can be overwritten — upgrade to a digest)
  2. Confirm key tags / enforced_params / audit logs are not on our critical path (known: they are not)
  3. Set "deeper DashScope needs / SSO / Postgres cost" as re-evaluation triggers; if one fires, run a parallel Bifrost POC via the migration CLI (production untouched)
  4. Optional: stand up a read-only Bifrost instance to evaluate semantic-cache gains (note the mandatory vector store)

09Unverified / open questions

Honesty boundary: none of the following could be confirmed from primary sources; do not rely on them in the decision.

  • Bifrost "durable execution": full docs index + repo search finds no "durable"; the closest features are async inference and the agent gateway. The claim is unconfirmable today
  • Whether the governance plugin needs explicit enabling: the OSS config docs and the Helm docs contradict each other; not live-tested
  • OSS/Enterprise boundary of Teams/Customers: the model-limits page explicitly marks customer/team scope "coming soon"; the full surface needs live testing
  • DashScope end-to-end usability: no official provider docs; whether compatible-mode-specific parameters (e.g. enable_search) pass through the openai base is unverified
  • Real semantic-cache benefit: no published hit-rate/cost-savings data; the vector-store requirement makes net gain unknown
  • Benchmark methodology gaps: all official numbers use mock upstreams; official and third-party figures are not intercomparable
  • Admin UI ergonomics (bulk team key issuance, report customization): judged from docs and UI source structure only, not hands-on
  • LiteLLM incident root cause: the official report says the investigation is in progress; deeper persistence cannot be ruled out yet
  • No Bifrost poisoning history: this is "not found", not "proven absent"
